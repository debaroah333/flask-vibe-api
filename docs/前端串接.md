# 個人記帳本前端串接規格書 (Frontend Integration Specification)

本文件依據《個人記帳本》之《交換格式.md》與《資料表設計.md》，為前端手機畫面與客戶端開發設計專案提供完整之串接分析與介面規格。前端工程師無需閱讀後端原始碼，即可依照本規格完成介接、狀態管理與表單驗證。

---

## 壹、共通規則

1. **外層三鍵結構 (Enveloping Schema)**
   所有 API 呼叫之回應最外層 JSON 物件固定且僅包含三個鍵：
   ```json
   {
     "code": 200,
     "message": "成功取得資料",
     "data": {}
   }
   ```
   - `code`（整數，`integer`）：業務狀態碼，與該次回應之 HTTP 狀態碼完全一致（例如 `200`、`201`、`400`、`404`、`500`）。
   - `message`（字串，`string`）：生活化、人性化之繁體中文說明訊息。嚴禁且絕不會在 JSON 內洩漏資料庫內部實體名稱（如資料表名、約束名）、SQLSTATE 代碼或系統堆疊追蹤（Stack Trace）。
   - `data`（物件 / 陣列 / null）：業務負載資料。
     - 成功取得單一物件或執行成功時為 JSON 物件 `{}`；
     - 成功取得清單時為 JSON 陣列 `[]`（查無符合條件之資料時回傳空陣列 `[]`）；
     - 失敗（`400`、`404`、`500`）或查詢特定 ID 不存在時，固定為 `null`。

2. **HTTP 狀態碼與情境對照**
   - `200 OK`：查詢成功、資料更新成功、交易作廢成功、對獎完成；清單無資料亦為 `200 OK`（`data: []`）。
   - `201 Created`：資源建立成功（回傳該筆資料，包含資料庫產生的識別碼 `id` 與建立時間 `created_at`）。
   - `400 Bad Request`：客戶端傳入資料格式有誤、必填欄位缺少、欄位長度或格式不合規、或違反業務約束條件（如名稱重複、金額小於等於 0、賣出股數大於持有庫存等）。
   - `404 Not Found`：路徑不存在，或以指定 `id` 查詢單筆資源但在資料庫查無對應資料（`data: null`）。
   - `500 Internal Server Error`：後端伺服器內部異常或資料庫暫時連不上（`data: null`）。

3. **客戶端不送的欄位 (Read-Only Fields)**
   - 客戶端在發送新增（`POST`）或局部更新（`PATCH`）請求時，**不應傳送**以下由系統維護的欄位：
     - `id`：資料庫遞增主鍵
     - `created_at`：建立時間戳記
     - `updated_at`：最後更新時間戳記
   - 若客戶端仍送入該等欄位，後端 API 嚴格予以忽略，不予處理也不會採用其值。

4. **日期、時間與金額型別規範**
   - **日期（Date）**：格式一律採用 ISO 8601 格式字串 `YYYY-MM-DD`（例如 `"2026-11-14"`）。前端表單需驗證合法年月日。
   - **時間戳記（Timestamp）**：後端回傳一律採用帶時區之 ISO 8601 UTC 字串（例如 `"2026-11-14T03:00:00+00:00"`）。
   - **金額、匯率、股數與價格（Numeric Values）**：
     - 在後端回應的 JSON 中一律以 JSON 數字（`number`，浮點數或整數）呈現，不帶任何貨幣符號、千分位逗號。
     - 前端發送請求時，數值欄位可傳送 JSON 數字（如 `70.0`）或合法的純數字字串（如 `"70.0"`），後端均能安全解析；負數與零在不允許之欄位會被後端驗證阻擋。

5. **可空欄位處理原則 (Nullability Handling)**
   - 資料庫中允許為空（Nullable）之欄位，後端回應時以 JSON `null` 呈現。
   - 客戶端在發送請求 payload 時，將欄位設為 `null`、傳送空字串（針對可空文字欄位）或直接省略該鍵具備完全相同之效果。

6. **識別碼說明**
   - 本文件中所有範例之 `id` 均為便於說明的整數展示（如 `1`、`2`），實際連線操作時，資源識別碼請一律以 API 回應之動態 `id` 為準。

## 貳、錯誤句子與代碼對照表

後端系統實施嚴格的內外錯誤訊息隔離原則：
- **伺服器應用日誌（Application Logs）**：記錄內部分類代碼 `error_code`、資料表名稱、約束名、SQLSTATE 及詳細例外。
- **對外 JSON 回應**：`code` 與 HTTP 代碼一致，`data` 為 `null`，`message` 呈現固定生活化繁體中文人話，**絕不出現在 JSON 負載中包含資料庫表名、約束名、SQLSTATE 或系統堆疊**。

| 內部錯誤代碼 (`error_code`) | HTTP 代碼 (`code`) | 客戶端人話訊息 (`message`) | 說明與觸發情境 |
| :--- | :---: | :--- | :--- |
| `validation.missing_required` | 400 | 缺少必填欄位 | 請求 JSON 缺少必填欄位，或欄位為空值 |
| `validation.invalid_format` | 400 | 欄位格式不正確 | 日期非 `YYYY-MM-DD`、期別不合規、發票號碼不符規則等 |
| `validation.out_of_range` | 400 | 數值超出允許範圍 | 金額/匯率 $\le 0$、結帳日不在 1~31 天等 |
| `conflict.unique_name` | 400 | 名稱已存在，請使用其他名稱 | 帳戶名稱、分類名稱、發票號碼或市場標的代號重複 |
| `conflict.foreign_key_missing` | 400 | 指派的關聯資源不存在 | 外鍵指向不存在的帳戶、分類、發票或標的識別碼 |
| `business.insufficient_holding` | 400 | 賣出數量超過目前持有股數 | 賣出或減資股數大於歷史重播當前持股庫存 |
| `business.cannot_void_claimed` | 400 | 此交易已關聯入帳記錄，不可作廢 | 欲作廢的交易已存在 `incomes` 關聯紀錄 |
| `resource.not_found` | 404 | 找不到這一筆 | 指定之 ID 在資料庫查無對應紀錄 |
| `upstream.twse` | 500 / 502 | 證交所目前沒有回應 | 外部台灣證券交易所行情連線超時、斷線或服務異常 |
| `database.connection_failed` | 500 | 資料庫暫時連不上 | 資料庫連線逾時、連線池耗盡或網路中斷 |

### 1. 系統健康檢查 (Health Check)

#### (1) 基礎伺服器健康檢查
- **方法與路徑**：`GET /api/health`
- **查詢參數**：無
- **請求欄位**：無
- **成功時 `data` 欄位**：
  - `status`（string，否）：伺服器狀態，固定為 `"ok"`
  - `time`（string，否）：目前伺服器時間 (ISO 8601 UTC)
- **最小 JSON 範例**：
```json
{
  "code": 200,
  "message": "伺服器運作正常，測試正常可以進行其他任務。",
  "data": {
    "status": "ok",
    "time": "2026-11-14T03:00:00+00:00"
  }
}
```

#### (2) 資料庫連線健康檢查
- **方法與路徑**：`GET /api/health/db`
- **查詢參數**：無
- **請求欄位**：無
- **成功時 `data` 欄位**：
  - `status`（string，否）：資料庫狀態，固定為 `"ok"`
- **最小 JSON 範例**：
```json
{
  "code": 200,
  "message": "資料庫連線正常",
  "data": {
    "status": "ok"
  }
}
```

### 2. 帳戶與餘額 (Accounts & Balance)

#### (1) 取得帳戶清單
- **方法與路徑**：`GET /api/accounts`
- **查詢參數**：無
- **請求欄位**：無
- **成功時 `data` 欄位**：陣列，每個元素包含：
  - `id`（integer，否）：帳戶識別碼
  - `name`（string，否）：帳戶名稱
  - `kind`（string，否）：種類（`cash`、`bank`、`credit_card`、`broker`）
  - `currency`（string，否）：幣別（預設 `TWD`）
  - `opening_balance`（number，否）：期初餘額
  - `statement_day`（integer，可空）：結帳日（1～31）
  - `payment_day`（integer，可空）：繳款日（1～31）
  - `created_at`（string，否）：建立時間
  - `updated_at`（string，否）：更新時間
- **最小 JSON 範例**：
```json
{
  "code": 200,
  "message": "成功取得帳戶清單",
  "data": [
    {
      "id": 1,
      "name": "現金錢包",
      "kind": "cash",
      "currency": "TWD",
      "opening_balance": 1000.0,
      "statement_day": null,
      "payment_day": null,
      "created_at": "2026-11-14T03:00:00+00:00",
      "updated_at": "2026-11-14T03:00:00+00:00"
    }
  ]
}
```

#### (2) 新增帳戶
- **方法與路徑**：`POST /api/accounts`
- **查詢參數**：無
- **請求欄位**：
  - `name`（string，必填）：帳戶名稱，最長 50 字元，不可與現有帳戶重複
  - `kind`（string，必填）：帳戶種類，僅限 `cash`、`bank`、`credit_card`、`broker`
  - `currency`（string，選填）：幣別代碼，預設為 `"TWD"`
  - `opening_balance`（number，選填）：期初餘額，預設為 `0.0`
  - `statement_day`（integer，選填）：結帳日（1～31）
  - `payment_day`（integer，選填）：繳款日（1～31）
- **成功時 `data` 欄位**：新增之帳戶物件
- **最小 JSON 範例**：
  - 請求：
  ```json
  {
    "name": "玉山銀行活存",
    "kind": "bank",
    "currency": "TWD",
    "opening_balance": 5000.0
  }
  ```
  - 回應：
  ```json
  {
    "code": 201,
    "message": "帳戶新增成功",
    "data": {
      "id": 2,
      "name": "玉山銀行活存",
      "kind": "bank",
      "currency": "TWD",
      "opening_balance": 5000.0,
      "statement_day": null,
      "payment_day": null,
      "created_at": "2026-11-14T03:05:00+00:00",
      "updated_at": "2026-11-14T03:05:00+00:00"
    }
  }
  ```

#### (3) 取得單筆帳戶資料
- **方法與路徑**：`GET /api/accounts/{id}`
- **查詢參數**：無
- **請求欄位**：無
- **成功時 `data` 欄位**：單一帳戶物件
- **最小 JSON 範例**：
```json
{
  "code": 200,
  "message": "成功取得帳戶資料",
  "data": {
    "id": 1,
    "name": "現金錢包",
    "kind": "cash",
    "currency": "TWD",
    "opening_balance": 1000.0,
    "statement_day": null,
    "payment_day": null,
    "created_at": "2026-11-14T03:00:00+00:00",
    "updated_at": "2026-11-14T03:00:00+00:00"
  }
}
```

#### (4) 更新帳戶資料
- **方法與路徑**：`PATCH /api/accounts/{id}`
- **查詢參數**：無
- **請求欄位**：
  - `name`（string，選填）：帳戶名稱
  - `statement_day`（integer，選填）：結帳日（1～31 或 `null`）
  - `payment_day`（integer，選填）：繳款日（1～31 或 `null`）
- **成功時 `data` 欄位**：更新後之帳戶物件
- **最小 JSON 範例**：
  - 請求：
  ```json
  {
    "name": "隨身小錢包"
  }
  ```
  - 回應：
  ```json
  {
    "code": 200,
    "message": "帳戶更新成功",
    "data": {
      "id": 1,
      "name": "隨身小錢包",
      "kind": "cash",
      "currency": "TWD",
      "opening_balance": 1000.0,
      "statement_day": null,
      "payment_day": null,
      "created_at": "2026-11-14T03:00:00+00:00",
      "updated_at": "2026-11-14T03:06:00+00:00"
    }
  }
  ```

#### (5) 查詢帳戶動態餘額
- **方法與路徑**：`GET /api/accounts/{id}/balance`
- **查詢參數**：無
- **請求欄位**：無
- **成功時 `data` 欄位**：
  - `account_id`（integer，否）：帳戶 ID
  - `account_name`（string，否）：帳戶名稱
  - `currency`（string，否）：帳戶原幣別
  - `opening_balance`（number，否）：期初餘額
  - `balance`（number，否）：帳戶當前原幣別餘額（建議使用）
  - `original_balance`（number，否）：原幣別餘額相容欄位
  - `balance_twd`（number，否）：換算為新台幣之當前餘額（建議使用）
  - `twd_balance`（number，否）：新台幣餘額相容欄位
- **最小 JSON 範例**：
```json
{
  "code": 200,
  "message": "成功取得帳戶餘額",
  "data": {
    "account_id": 1,
    "account_name": "現金錢包",
    "currency": "TWD",
    "opening_balance": 1000.0,
    "balance": 1700.0,
    "original_balance": 1700.0,
    "balance_twd": 1700.0,
    "twd_balance": 1700.0
  }
}
```

### 3. 帳戶移轉 (Transfers)

#### (1) 取得移轉清單
- **方法與路徑**：`GET /api/transfers`
- **查詢參數**：無
- **請求欄位**：無
- **成功時 `data` 欄位**：陣列，每個元素包含：
  - `id`（integer，否）：移轉 ID
  - `transferred_on`（string，否）：移轉日期 (`YYYY-MM-DD`)
  - `amount`（number，否）：移轉金額
  - `currency`（string，否）：幣別代碼
  - `fx_rate_to_twd`（number，否）：台幣匯率
  - `from_account_id`（integer，否）：轉出帳戶 ID
  - `to_account_id`（integer，否）：轉入帳戶 ID
  - `note`（string，可空）：備註說明
  - `created_at`（string，否）：建立時間
  - `updated_at`（string，否）：更新時間
- **最小 JSON 範例**：
```json
{
  "code": 200,
  "message": "成功取得移轉清單",
  "data": [
    {
      "id": 1,
      "transferred_on": "2026-11-14",
      "amount": 200.0,
      "currency": "TWD",
      "fx_rate_to_twd": 1.0,
      "from_account_id": 2,
      "to_account_id": 1,
      "note": "ATM 提款",
      "created_at": "2026-11-14T03:10:00+00:00",
      "updated_at": "2026-11-14T03:10:00+00:00"
    }
  ]
}
```

#### (2) 新增移轉
- **方法與路徑**：`POST /api/transfers`
- **查詢參數**：無
- **請求欄位**：
  - `transferred_on`（string，必填）：移轉日期，格式 `YYYY-MM-DD`
  - `amount`（number，必填）：移轉金額，必須 $> 0$
  - `currency`（string，選填）：幣別代碼，預設為 `"TWD"`
  - `fx_rate_to_twd`（number，選填）：換算新台幣匯率，TWD 時預設為 `1.0`
  - `from_account_id`（integer，必填）：轉出帳戶 ID
  - `to_account_id`（integer，必填）：轉入帳戶 ID，不可與轉出相同
  - `note`（string，選填）：備註說明
- **成功時 `data` 欄位**：建立之移轉物件
- **最小 JSON 範例**：
  - 請求：
  ```json
  {
    "transferred_on": "2026-11-14",
    "amount": 200.0,
    "from_account_id": 2,
    "to_account_id": 1,
    "note": "ATM 提款"
  }
  ```
  - 回應：
  ```json
  {
    "code": 201,
    "message": "移轉記錄新增成功",
    "data": {
      "id": 1,
      "transferred_on": "2026-11-14",
      "amount": 200.0,
      "currency": "TWD",
      "fx_rate_to_twd": 1.0,
      "from_account_id": 2,
      "to_account_id": 1,
      "note": "ATM 提款",
      "created_at": "2026-11-14T03:10:00+00:00",
      "updated_at": "2026-11-14T03:10:00+00:00"
    }
  }
  ```

  - `trade_type`（string，必填）：交易種類，限 `buy`、`sell`、`cash_dividend`、`stock_dividend`、`drip`、`split`、`merge`、`capital_reduction`
  - `traded_on`（string，必填）：交易生效日期，格式 `YYYY-MM-DD`
  - `currency`（string，必填）：結算幣別（3 碼）

  - **種類關聯數值欄位（依種類必填/選填）**：

- **最小 JSON 範例**：
  - 請求：
  ```json

    "instrument_id": 1,
  ```

## 伍、交換格式與資料表設計的差異分析

經比對《docs/交換格式.md》與《docs/資料表設計.md》，發現部分欄位命名、結構與約束在兩份規格間存在差異。依專案規範，**嚴格禁止更動《交換格式.md》與《資料表設計.md》，亦不改動現有 Python 程式碼**。前端介接時**一律以《交換格式.md》及後端現有回傳 JSON 為準**。

以下逐條整理差異對照，供前後端團隊後續溝通與維護參照：

### 1. 帳戶 (Accounts)
- **欄位 `kind` vs `account_type`**：
  - 《交換格式》：欄位名為 `kind`，列舉值為 `cash`、`bank`、`credit_card`、`broker`。
  - 《資料表設計》：欄位名為 `account_type`，列舉值為 `cash`、`bank`、`credit_card`、`brokerage_settlement`。
  - *前端串接*：使用 `kind`。
- **期初餘額與信用卡週期欄位**：
  - 《交換格式》：定義有 `opening_balance`（number，預設 0.0）、`statement_day`（integer，可空）、`payment_day`（integer，可空）。
  - 《資料表設計》：未於 `accounts` 表定義此三欄位（設計書中餘額全由交易流水動態衍生）。
  - *前端串接*：前端需提交與讀取 `opening_balance`、`statement_day`、`payment_day`。
- **帳戶備註與啟用狀態**：
  - 《資料表設計》：定義有 `is_active`（boolean）與 `note`（text）。
  - 《交換格式》：未公開 `is_active` 與 `note`。
  - *前端串接*：前端不傳送亦不處理 `is_active` 與 `note`。

### 2. 帳戶移轉 (Transfers)
- **欄位 `transferred_on` vs `transferred_at`**：
  - 《交換格式》：`transferred_on`（字串，日期格式 `YYYY-MM-DD`）。
  - 《資料表設計》：`transferred_at`（`timestamptz`，含時區時間戳記）。
  - *前端串接*：前端送出與接收 `transferred_on`（`YYYY-MM-DD`）。
- **單一金額/幣別 vs 雙向金額/幣別**：
  - 《交換格式》：採用單一 `amount`、`currency`、`fx_rate_to_twd`。
  - 《資料表設計》：定義有 `from_amount`、`to_amount`、`from_currency`、`to_currency`、`twd_exchange_rate`。
  - *前端串接*：使用 `amount`、`currency`、`fx_rate_to_twd`。

### 3. 分類說明欄位 (`description` vs `note`)
- **入帳分類與花費分類**：
  - 《交換格式》/ 程式實作：欄位為 `description`（字串，可空）。
  - 《資料表設計》：欄位為 `note`（text，可空）。
  - *前端串接*：使用 `description`。

### 4. 入帳明細 (Incomes)
- **日期欄位與匯率欄位**：
  - 《交換格式》：日期為 `received_on`（`YYYY-MM-DD`），匯率為 `fx_rate_to_twd`。
  - 《資料表設計》：時間為 `received_at`（`timestamptz`），匯率為 `twd_exchange_rate`。
  - *前端串接*：使用 `received_on` 與 `fx_rate_to_twd`。
- **描述約束 (`source` 與 `note`)**：
  - 《交換格式》：包含 `source` 與 `note` 兩欄，並由業務規則強制約束「兩者至少一個不可為空」。
  - 《資料表設計》：僅包含 `note`（可空），無 `source` 欄位。
  - *前端串接*：表單需包含 `source` 或 `note`，且至少填寫一項。
- **投資關聯鍵名**：
  - 《交換格式》：欄位名為 `trade_id`。
  - 《資料表設計》：外鍵欄位名為 `investment_transaction_id`。
  - *前端串接*：使用 `trade_id`。

### 5. 花費明細 (Expenses)
- **日期欄位與匯率欄位**：
  - 《交換格式》：消費日為 `spent_on`（`YYYY-MM-DD`），結算日為 `settled_on`（`YYYY-MM-DD`），匯率為 `fx_rate_to_twd`。
  - 《資料表設計》：消費時間為 `spent_at`（`timestamptz`），結算時間為 `billed_at`（`timestamptz`），匯率為 `twd_exchange_rate`。
  - *前端串接*：使用 `spent_on`、`settled_on` 與 `fx_rate_to_twd`。
- **商家約束 (`merchant` 與 `note`)**：
  - 《交換格式》：包含 `merchant` 與 `note` 兩欄，強制約束「兩者至少一個不可為空」。
  - 《資料表設計》：僅包含 `note`（可空），無 `merchant` 欄位。
  - *前端串接*：表單需包含 `merchant` 或 `note`，且至少填寫一項。

### 6. 統一發票 (Invoices)
- **發票號碼、日期與總額**：
  - 《交換格式》：號碼為 `number`，開立日為 `issued_on`（`YYYY-MM-DD`），金額為 `amount`。
  - 《資料表設計》：號碼為 `invoice_number`，開立時間為 `issued_at`（`timestamptz`），金額為 `total_amount`。
  - *前端串接*：使用 `number`、`issued_on`、`amount`。
- **發票種類、幣別與隨機碼**：
  - 《交換格式》：包含 `kind`（`paper`, `electronic`）、`currency`、`fx_rate_to_twd`、`random_code`（4 碼數字）。
  - 《資料表設計》：未包含上述四項欄位。
  - *前端串接*：依照《交換格式》處理上述欄位。
- **賣方統編與中獎狀態**：
  - 《交換格式》：賣方統編為 `seller_ban`，中獎狀態為字串欄位 `prize_status`（`unchecked`、`lost`、`won`、`claimed`、`void`）。
  - 《資料表設計》：賣方統編為 `seller_tax_id`，中獎以 `prize_tier_id` 外鍵關聯。
  - *前端串接*：使用 `seller_ban` 與 `prize_status`。
- **期別與單筆關聯資料**：
  - 《資料表設計》：包含欄位 `period`（`char(6)`，如 `202602`）。
  - 《交換格式》：發票本體無 `period` 欄位，由 `issued_on` 動態推算期別；單筆查詢額外附帶品項陣列 `items` 與關聯花費識別碼清單 `expense_ids`。
  - *前端串接*：前端解構單筆回應時可直接取用 `items` 與 `expense_ids`。

### 7. 發票品項 (Invoice Items)
- **品項名稱與小計金額**：
  - 《交換格式》：品名為 `name`，小計為 `line_amount`。
  - 《資料表設計》：品名為 `item_name`，小計為 `subtotal`。
  - *前端串接*：使用 `name` 與 `line_amount`。

### 8. 開獎期別與獎項定義架構
- 《資料表設計》：規劃 `invoice_draws`（一期一列，欄位展開 `special_prize_number`、`grand_prize_number`、`first_prize_numbers`）與 `invoice_prize_tiers`（法定獎項定義）。
- 《交換格式》/ 實作：將其正規劃為 `draw_periods`（期別表，`period_key` 為 `YYYY-01` 格式）與子表 `draw_prizes`（以 `tier`、`matching_number`、`amount` 記錄每筆獎號與獎金），透過 `/api/draw-periods/{id}/check` 批次對獎。
- *前端串接*：依現行開獎與對獎端點進行串接。

### 9. 投資標的 (Instruments vs Investment Targets)
- **實體名稱與欄位**：
  - 《交換格式》：實體為 `instruments`，欄位為 `id`, `market`, `symbol`, `name`, `currency`。唯一約束為複合鍵 `UNIQUE(market, symbol)`。
  - 《資料表設計》：表名為 `investment_targets`，欄位為 `id`, `symbol`, `name`, `asset_type`, `currency`, `market`, `note`。唯一約束為單一鍵 `UNIQUE(symbol)`。
  - *前端串接*：標的型態由 `market` 呈現（`tw_stock`, `us_stock`, `fund`, `other`），無獨立 `asset_type` 欄位。

### 10. 投資交易 (Trades vs Investment Transactions)
- **實體名稱與交易欄位**：
  - 《交換格式》：實體為 `trades`，標的關聯為 `instrument_id`，日期為 `traded_on`（`YYYY-MM-DD`），數量為 `quantity`，單價為 `price`，比例為 `ratio`，匯率為 `fx_rate_to_twd`。
  - 《資料表設計》：實體為 `investment_transactions`，標的關聯為 `target_id`，成交時間為 `transacted_at`（`timestamptz`），股數為 `shares`，單價為 `price_per_share`，比例為 `split_ratio_from` 與 `split_ratio_to`，匯率為 `twd_exchange_rate`。
  - *前端串接*：使用 `instrument_id`、`traded_on`、`quantity`、`price`、`ratio`、`fx_rate_to_twd`。
- **交易作廢支援**：
  - 《交換格式》/ 實作：包含 `voided_at` 欄位，提供 `POST /api/trades/{id}/void` 端點作廢交易，且持倉計算會自動忽略作廢交易。
  - 《資料表設計》：設計原則不引入軟刪除或作廢標記，規劃以反向沖銷列處理。
  - *前端串接*：前端如需作廢交易，呼叫 `/api/trades/{id}/void`，並依 `voided_at` 是否為 `null` 呈現作廢標籤。
