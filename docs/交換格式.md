# 個人記帳本 API 交換格式規格書 (Exchange Format Specification)

本文件依據《個人記帳本》規格定義前後端資料交換標準格式。前端應用程式僅需參照本規格進行介接與狀態處理，無需閱讀後端原始程式碼。

---

## 壹、共通規則

1. **外層三鍵結構**
   所有 API 回應（無論成功或失敗）的最外層 JSON 物件固定且僅包含三個鍵：
   ```json
   {
     "code": 200,
     "message": "成功取得資料",
     "data": {}
   }
   ```
   - `code`（整數）：業務與 HTTP 狀態碼對應值。
   - `message`（字串）：人性化繁體中文說明訊息，嚴禁包含資料庫內部表名、約束名、SQLSTATE 或堆疊追蹤。
   - `data`（物件 / 陣列 / null）：業務負載資料。失敗或查無該筆單一資源時固定為 `null`；清單無資料時為空陣列 `[]`。

2. **HTTP 狀態碼對照**
   - `200 OK`：查詢成功、更新成功、作廢成功、對獎完成；若清單為空亦回傳 `200`（`data: []`）。
   - `201 Created`：資源新增成功（回傳該列資料，含新產生的 `id` 與 `created_at`）。
   - `400 Bad Request`：格式錯誤、必填欄位缺漏、違反業務規則或資料庫約束（如名稱重複、金額小於等於 0、賣出超過持有量等）。
   - `404 Not Found`：指定識別碼的單一資源不存在（`data: null`）。
   - `500 Internal Server Error`：伺服器內部錯誤或資料庫連線失敗（`data: null`）。

3. **客戶端不送的欄位**
   - 客戶端在發送 `POST` 或 `PATCH` 請求時，不應送出代理主鍵 `id` 及建立時間 `created_at`。
   - 若客戶端仍送入該些欄位，後端 API 嚴格予以忽略，絕不採用。

4. **日期、時間與金額型別規範**
   - **日期（Date）**：格式一律採用 ISO 8601 格式字串 `YYYY-MM-DD`（例如 `"2026-11-14"`）。
   - **時間戳記（Timestamp）**：一律採用帶時區之 ISO 8601 UTC 字串（例如 `"2026-11-14T03:00:00+00:00"`）。
   - **金額與數值（Amount / Rate / Quantity / Price）**：在 JSON 回應中以浮點數（`number`）呈現；前端送出時可為數字或數值字串。

5. **可空欄位處理原則**
   - 可為空的欄位在後端回應中以 `null` 出現。
   - 客戶端在發送請求時，將欄位設為 `null` 與省略該欄位具備完全相同之效果。

## 貳、資源規格與回應範例

> **說明**：各資源範例資料均採用 Postman 測試情境資料；範例中的 `id` 統一由 `1` 起算展示，實際連線操作請以 API 回應之動態 `id` 為準。

### 1. 帳戶 (Accounts)

- **情境資料**：現金錢包（日常現金包）

#### (1) 成功回應範例 (`POST /api/accounts` 或 `GET /api/accounts/1`)
```json
{
  "code": 201,
  "message": "帳戶新增成功",
  "data": {
    "id": 1,
    "name": "現金錢包",
    "kind": "cash",
    "currency": "TWD",
    "opening_balance": 1000.0,
    "statement_day": null,
    "payment_day": null,
    "created_at": "2026-11-14T03:00:00+00:00",
    "updated_at": "2026-11-14T03:00:00+00:00"
  }
}
```

#### (2) 欄位定義表
| 欄位名稱 | 型別 | 可空 | 說明 |
| :--- | :--- | :---: | :--- |
| `id` | integer | 否 | 帳戶唯一識別碼 |
| `name` | string | 否 | 帳戶名稱（全系統唯一） |
| `kind` | string | 否 | 帳戶種類：`cash`、`bank`、`credit_card`、`broker` |
| `currency` | string | 否 | 結算幣別（預設 `TWD`） |
| `opening_balance` | number | 否 | 期初餘額（預設 `0.0`） |
| `statement_day` | integer | 是 | 結帳日（1～31，信用卡適用） |
| `payment_day` | integer | 是 | 繳款日（1～31，信用卡適用） |
| `created_at` | string | 否 | 建立時間戳記 (ISO 8601 UTC) |
| `updated_at` | string | 否 | 最後更新時間戳記 (ISO 8601 UTC) |

## 肆、內部錯誤與日誌規範 (Internal Errors & Logging)

**重要規範**：
以下所定義之日誌鍵名、錯誤代碼與結構**僅記錄於伺服器端應用程式日誌 (Application Logs)**，嚴禁回傳給客戶端，亦不得出現在回應之 JSON 負載中，以避免洩漏資料庫架構或系統實作細節。

### 1. 伺服器日誌物件鍵名定義
- `timestamp`：ISO 8601 格式之 UTC 事件記錄時間戳記。
- `level`：記錄層級（如 `WARNING`、`ERROR`）。
- `error_code`：分類錯誤識別碼（格式例如 `domain.reason`）。
- `endpoint`：觸發該錯誤之 HTTP 方法與路由路徑（如 `POST /api/accounts`）。
- `detail`：底層錯誤原因、資料庫表名、違反約束名稱或參數細節。
- `client_ip`：發出該請求之客戶端 IP 位址。

### 2. 內部 `error_code` 對照表
| 內部錯誤代碼 | HTTP 代碼 | 人性化對外訊息 (`message`) | 內部觸發原因說明 |
| :--- | :---: | :--- | :--- |
| `validation.missing_required` | 400 | 缺少必填欄位 | 請求 JSON 物件中缺少必要的必填欄位 |
| `validation.invalid_format` | 400 | 欄位格式不正確 | 日期、幣別長度或發票號碼正規式不符 |
| `validation.out_of_range` | 400 | 數值超出允許範圍 | 金額/匯率 $\le 0$、結帳日不在 1~31 範圍 |
| `conflict.unique_name` | 400 | 名稱已存在，請使用其他名稱 | 帳戶名稱、分類名稱或市場標的代號重複 |
| `conflict.foreign_key_missing` | 400 | 指派的關聯資源不存在 | 外鍵指向不存在的帳戶、分類、發票或標的 |
| `business.insufficient_holding` | 400 | 賣出數量超過目前持有股數 | 賣出或減資股數大於歷史重播當前持股數 |
| `business.cannot_void_claimed` | 400 | 此交易已關聯入帳記錄，不可作廢 | 欲作廢的交易已存在 `incomes` 關聯紀錄 |
| `resource.not_found` | 404 | 找不到這一筆 | 指定之 ID 在資料庫中查無對應列 |
| `database.connection_failed` | 500 | 資料庫暫時連不上 | 資料庫連線池耗盡、網路斷線或資料庫異常 |

### 3. `conflict.unique_name` 伺服器內部日誌範例
```json
{
  "timestamp": "2026-11-14T03:00:15.123456Z",
  "level": "WARNING",
  "error_code": "conflict.unique_name",
  "endpoint": "POST /api/accounts",
  "client_ip": "127.0.0.1",
  "detail": {
    "table": "accounts",
    "constraint": "accounts_name_key",
    "conflicting_value": "現金錢包",
    "sqlstate": "23505"
  }
}
```

## 伍、清單查詢參數規範 (Query Parameters)

所有查詢參數均為選填（唯 `GET /api/summary` 的 `month` 為必填）。傳送時參數與 SQL 語法嚴格分離，參數值以 URL Query String 形式傳遞。

| 資源端點 | 查詢參數 | 型別 | 說明與範例 |
